# zapisynagry — technical documentation

Plain PHP, no framework. SQLite via PDO. Server-rendered pages, a little
progressive-enhancement JavaScript, no build step.

The guiding constraint is cheap shared hosting: upload files, open a URL, done.
Everything below follows from that.

## 1. Requirements and deployment

**PHP 7.4+** (`MIN_PHP_VERSION` in `install.php`), extensions `pdo_sqlite`,
`curl`, `zip`, `gd`, `mbstring`, `simplexml` (BGG search parses XML with it —
without it, a search fatals rather than degrading). No Composer step — `vendor/` contains only
PHPMailer, committed to the repo.

**Installing.** Upload `install.php` alone and open it. It downloads the branch
zip from GitHub, unpacks it, runs `database.sql`, writes `config.php` (which
defines `DB_PATH`), drops a deny-all `.htaccess` into `data/`, creates the first
admin, then deletes itself.

**Updating.** Admin panel → Update. Same download, overlaid onto the existing
install, followed by a schema migration. See [§10](#10-the-updater).

**`.htaccess`** in the root provides extensionless aliases (`/admin` →
`admin.php`) for single-segment paths only, and blocks `data/`. The aliases are
never generated by the app — nothing links to them — so they can only add a way
in, never break one. See the comments in the file for why paths with slashes are
deliberately excluded.

## 2. Directory layout

```
/                 page controllers, one file per URL
/inc              the core library (see §4)
/inc/admin        one controller per admin tab
/templates/<theme>/   view files; light is the base, others override selectively
/languages        pl.php, en.php — flat key => string arrays
/js               scripts.js, the only script file
/img, /icons      static assets; icons/ is admin-uploadable
/thumbnails       uploaded and cached game images
/data             database.sqlite (deny-all .htaccess)
/vendor           PHPMailer
/tests            the test suite; excluded from GitHub deployments
```

**Web root holds only real pages.** Anything in `/` that is not a controller is a
mistake — four stale template copies once accumulated there and fatalled when
requested. `tests/test_smoke.php` now loads every file in the root, so this
cannot recur silently.

## 3. Request lifecycle

Every page begins with `require inc/bootstrap.php`, which loads the library in
dependency order and then wires up the request. **The order matters:**

```php
require config.php        // DB_PATH
require helpers.php, db.php, options.php, lang.php, template.php, auth.php
date_default_timezone_set('UTC');   // safe baseline
options_load();                     // opt*() usable from here
app_timezone_init();                // switch to the configured timezone
auth_init();                        // session; current_user(), csrf_*, flash
csrf_token();                       // mint early, while headers can still be sent
lang_load();                        // t() usable from here
tpl_init();                         // tpl_render() usable from here
```

Why each step sits where it does:

- **`options_load()` before `auth_init()`** — the session restore reads
  `opt_int('login_days')`; with a cold cache it would see 0 and clamp every
  token lifetime to the one-day floor.
- **`app_timezone_init()` after `options_load()`** — it needs `opt()`. The UTC
  line above it is only a baseline so nothing reads an unconfigured clock.
- **`csrf_token()` early** — it refreshes a mirror cookie, which needs headers
  not yet sent. A page whose first `csrf_field()` call comes from the footer
  would be too late.

A controller then does its work and calls `tpl_render('header', …)`, one or more
body templates, and `tpl_render('footer', …)`.

**Includes use plain `require`, not `require_once`**, and rely on ordering. Do
not "helpfully" add a `require_once` inside a library file: if another script
plain-requires the same file later you get *cannot redeclare*. This is why
`inc/mailing.php` reads `opt_bool('send_emails')` directly instead of calling
`notify_enabled()` — see the comment at the top of that file.

**Database access.** Four helpers only — `db_run` (write), `db_one` (a row),
`db_all` (rows), `db_val` (a single scalar). There is no `db_col`. All take
bound parameters; never interpolate into SQL.

## 5. Data model

`database.sql` is the **single source of truth** for both a fresh install and
migrations. It is executed verbatim on install, and diffed against the live
database on update.

Tables:

```
meta                     schema bookkeeping
options                  admin settings (53 rows, key => value)
users, auth_tokens, password_resets
events                   one row per event; is_archived makes it read-only
event_days               day_index, day_date, start_time, end_time
game_tables              tables, numbered within a day
games, players           games and their signups (players.is_reserve)
polls, poll_games, poll_votes
comments, poll_comments
mail_subscribers         per-event mailing list
predefined_thumbnails, verification_codes, logs
```

Notes that catch people out:

- **A guest-created row stores `NULL` in its user column**, not `0`. There are
  foreign keys to `users`, so `WHERE proposer_user_id = 0` silently matches
  nothing.
- **Timestamps come from two clocks.** `created_at` columns default to SQLite's
  `datetime('now')`, which is always UTC and is only ever *displayed*. Values
  PHP writes (`polls.deadline`, `auth_tokens.expires_at`) use `date()` on the
  configured timezone. Verification and password-reset expiries use `gmdate()`
  on both sides. Never compare across these groups.
- **Options are strings.** Use `opt_bool` / `opt_int` rather than comparing the
  raw value.

## 6. Themes and templates

Three themes in `templates/`: **light** (the base — `BASE_TEMPLATE`), **dark**
and **classic**.

`tpl_file()` resolves a name against the active theme first, then falls back to
light. So a theme only needs the files it wants to change: `dark/` is a
stylesheet alone, and `classic/` overrides one template plus its CSS.

Non-base stylesheets `@import` light's, then override. Only the active theme's
sheet is ever linked.

Templates are **presentation only**. They receive an explicit array of variables
and never query the database — `tpl_render()` extracts that array into scope,
using `$__tpl_*` locals internally to avoid collisions.

**Prefer restyling shared markup over forking a template.** Once classic forked
`game_card.php`, its comment button drifted out of sync with the poll card's for
months. Everything the classic poll card does is CSS against light's markup.

**All page URLs are relative and root-less** (`templates/light/css/style.css`,
`icons/…`, `js/scripts.js`). This is what makes path-style pretty URLs a large
job rather than an `.htaccess` change — under `/add_game/18` the browser resolves
those against `/add_game/`.

## 7. Translations

`languages/pl.php` and `en.php` return flat `key => string` arrays. Look-up is
`t('key')`, with `sprintf` arguments: `t('ml_admin_sent', $n)`.

**Add every new key to both files in the same commit.** Duplicate keys silently
overwrite each other; the test suite has a guard for that. Prefix related keys
(`ml_*`, `msgbtn_*`) to avoid collisions.

Strings needed by JavaScript are exposed through `window.APP_LANG` in
`header.php` — see the deadline preview for the pattern.

## 8. Permissions

Three overlapping systems; use the right one.

1. **Accounts** — `is_logged_in()`, `is_admin()`, `require_login()`,
   `require_admin()`.
2. **Feature gates** — `can_add_games()`, `can_signup()`, `messaging_allowed()`,
   `mailing_enabled()`: option-driven, about what the *site* permits.
3. **Ownership** — `verify_can_show_buttons($ownerUserId)` and
   `verify_decision()`. A row created by an account can be edited only by that
   account or an admin; a guest-created one falls into a verification tree
   (`allow` / `email_match` / `email_code` / `deny`) set by the
   `verification_method` option.

**A button is not a permission.** Templates hide controls; the controller must
re-check. Every destructive page repeats the check server-side, and the tests
POST directly to prove it.

CSRF: `csrf_field()` in the form, `csrf_check()` in the handler. The token is
mirrored into a 30-day HttpOnly cookie so it survives shared-host session GC,
and is rotated on login and logout.

## 9. Domain rules worth knowing

**Overnight days.** A day may run 18:00 → 03:00. `day_rel_min($hhmm, $dayStart)`
converts a wall-clock time into minutes from the day's opening, adding 1440 for
times past midnight. The pivot is the opening hour minus
`overnight_grace_hours`, so a pre-opening setup slot still counts as that
evening. Anything ordering or scheduling times must go through it — pasting
`day_date . ' ' . $start_time` is wrong on these days and was a real bug.

**Poll resolution.** `poll_check_resolve()` runs after every vote. By default the
first candidate to reach its `required_players` wins immediately. If the poll has
`wait_for_deadline = 1` **and** a deadline, the threshold is ignored and only
`poll_resolve_expired()` (called on page load from `index.php`) or a manual end
resolves it. The flag is deliberately ignored without a deadline, or the poll
could never finish.

**Deadlines** are stored absolute but edited as *hours before the start*. The
three conversions live in `inc/polls.php` (`poll_start_ts`,
`poll_deadline_from_hours`, `poll_deadline_hours`); a deadline already in the
past is clamped to an hour from now.

**Reserves.** `promote_reserves()` fills freed seats in order. Call it after any
removal.

**Input validation.** "No apostrophes" means rejecting entries made *only* of
punctuation — `text_has_content()`. Titles like *Tzolk'in* must pass.

## 10. The updater

`update_run()` downloads the branch zip, overlays it onto the install, then
migrates the schema by diffing the live database against `database.sql`:

- **missing tables** → created from the reference `CREATE TABLE`
- **missing columns** → `ALTER TABLE … ADD COLUMN` (`update_addcolumn_sql`)
- **missing indexes** → created from the reference `CREATE INDEX`
- **missing options keys** → inserted with their default; existing values are
  never overwritten

It then calls `opcache_reset()` and `clearstatcache()`, or the old bytecode
lingers.

**It only ever adds, and never deletes.** Files removed from the repo stay on the
server, so deletions must be done by hand. Local-only indexes are left alone.

Two separate exclusion lists govern the overlay, and they mean opposite things:

- **`update_protected_paths()`** — things the *server* owns, never overwritten:
  `config.php`, `data`, `thumbnails`, `icons`, `install.php`. Copying over any of
  them would destroy something the admin owns.
- **`update_skipped_paths()`** — things the *release* ships but must not deploy:
  `docs`, `tests`. Developer documentation has no business being publicly
  readable in a web root, and the test suite would be actively undesirable on a
  live install.

Both are matched against top-level names only.

`.htaccess` is in neither list — it ships from the repo, so edit it there rather
than on the server, or the next update overwrites your changes.

Because the updater never deletes, a folder that *was* deployed by an older
release stays until removed by hand. If `docs/` reached your server before this
exclusion existed, delete it once.

To add a column or table, edit `database.sql` and nothing else. Give new columns
`NOT NULL DEFAULT` so existing rows stay valid.

## 11. Tests

`tests/` is standalone and excluded from deployment by `update_skipped_paths()`,
so it may safely live in the repository. Run everything with `php tests/run.php`; it auto-discovers `test_*.php` and exits non-zero on
failure.

Each suite calls `tg_setup()`, asserts with `ok($cond, $label)`, groups with
`section()`, and ends with `tg_result()`. Helpers:

| Helper | Use |
|---|---|
| `tg_get($uid, $script, $get)` | Render a page as a GET, in a fresh child process. |
| `tg_page($uid, $script, $get, $post)` | Same, as a POST. |
| `tg_page_session(…, $session)` | POST with extra session state seeded (e.g. a poll draft). |
| `tg_tpl($tpl, $uid, $script, $vars)` | Render one template directly. |
| `tg_controller($ctlPath, $uid, $post)` | Run an admin tab controller. |
| `tg_eval($phpExpr, $uid)` | Evaluate a snippet inside a booted app. |
| `tg_set_opt($key, $val)` | Write an option. |

Two structural guards exist because both failures actually happened:

- **`tg_guard()`** fails the run on any PHP fatal in a child process. A fatal
  mid-render still returns the markup echoed before it, so a substring assertion
  can pass against a dying page.
- **`run.php`** refuses to run a suite with more than one `tg_result()`, or with
  code after it. A stray one silently discarded every later test in that file.

Gotchas: `tg_set_opt()` writes the database but does not refresh the *current*
process's option cache — call `options_load()` if the same process then reads it.
Child processes reload on their own. POST helpers never retry, because retrying a
redirect would double the insert.

## 12. How to make common changes

**Add a page.** Create `foo.php` in the root, `require inc/bootstrap.php` plus
whatever modules it needs, do the work, then `tpl_render('header'…)`,
`tpl_render('foo'…)`, `tpl_render('footer')`. Add `templates/light/foo.php`. Add
it to the `$pages` list in `tests/test_smoke.php` — the suite fails if you
don't.

**Add an option.** One row in `database.sql`'s options seed, the key in
`inc/admin/options.php` (`$OPTION_VALUES` for text, `$OPTION_TOGGLES` for a
checkbox — miss this and the field renders but never saves), a field in
`templates/light/admin_options.php`, and `opt_*` labels in both language files.

**Add a column.** Edit `database.sql` only. Use `NOT NULL DEFAULT`.

**Add a notification.** A function in `inc/notify.php` gated on
`notify_enabled()`, called from the controller *after* the commit — outside the
transaction, so slow SMTP holds no write lock and a rollback sends nothing.

**Add a theme.** `templates/<name>/css/style.css` that `@import`s light's. Add
files only for markup you actually need to change.

**Add a translation key.** Both files, same commit.

## 13. Traps

Each of these has bitten at least once.

- **`require_once` in a library file** → *cannot redeclare* when another script
  plain-requires it later.
- **A missing `require`** only fatals at runtime, and the page still returns
  everything printed before the crash. Run the smoke suite.
- **An absent form field is not an empty one.** A checkbox that is genuinely on
  the form means "unticked" when absent; a field hidden by the current mode, or
  missing from a partial POST, must keep its stored value. `edit_poll.php`
  distinguishes both cases explicitly.
- **`opt()` is cached.** `opt_set()` inside one request does not change what a
  later `opt()` in that same request sees unless the cache is reloaded.
- **Stray files in the web root** are publicly reachable and will fatal. Nothing
  belongs in `/` but page controllers.
- **CSS specificity.** `.btn-danger` once had no `:hover`, so `.btn-small:hover`
  — same specificity, defined earlier — repainted red buttons grey. A variant
  must restate every property the base's hover sets.
- **Relative URLs.** Every asset path assumes the page lives at `/`.
